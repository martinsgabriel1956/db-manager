# Ordo — Decisões de design (v1)

> O app se chamava DB Manager até a v1; o identificador `dev.nemomartins.dbmanager` e o serviço do keychain `db-manager` continuam com o nome antigo para não perder conexões e senhas salvas.

Resultado da sessão de grill de 2026-10-10. Uso pessoal, um único usuário.

## Produto

- Cliente desktop para gerenciar bancos existentes (estilo TablePlus/DBeaver).
- Engines v1: **Postgres, MySQL, SQLite, MongoDB, Redis (standalone)**.
- Três UIs: grade relacional (SQL), documento (Mongo), chave-valor (Redis).

## Stack

- **Tauri** + **React + Vite** (front) + **Rust puro** (backend via comandos Tauri/IPC, sem servidor HTTP).
- Drivers: `sqlx` (pg/mysql/sqlite), `mongodb`, `redis`. Sem ORM.
- Contrato tipado: `tauri-specta` gera os tipos TS a partir do Rust.
- Front: TanStack Query (estado do Rust), Zustand + `persist` via `tauri-plugin-store` (estado de UI), TanStack Table + Virtual, Tailwind + shadcn/ui, CodeMirror 6, `react-resizable-panels`, React Flow + `elkjs`, Zod só em formulários. Sem roteador.

## Conexões

- Metadados em JSON (diretório de dados do app); senha/URI no keychain do SO (crate `keyring`, chave `db-manager:<id>`).
- Linux sem Secret Service: fallback com aviso claro na UI, nunca texto puro silencioso.
- TLS na v1 (modo + CA opcional). Túnel SSH depois da v1 (ver "Depois da v1").

## UI SQL

- Árvore conexão → schema → tabelas/views.
- Navegação paginada, ordenação, filtro simples (SQL parametrizado).
- Edição inline **em stage**, aplicada numa transação; **só em tabela com PK**, senão somente leitura.
- Editor SQL (CodeMirror, autocomplete), executar seleção ou script.
- Estrutura da tabela (somente leitura): colunas, índices, FKs.
- Múltiplas abas (persistidas), histórico de queries (SQLite local, com busca), export CSV (streaming para arquivo), diagrama ER (somente leitura, a partir das FKs).
- Fora: edição de schema pela UI (entrou depois da v1: ver "Depois da v1").

## UI MongoDB

- Árvore databases → collections (+ índices: criar e remover, ver "Depois da v1").
- Filtro, sort e projection em JSON; visualização em árvore ou JSON cru.
- CRUD por documento (`replaceOne` por `_id`, sem stage).
- **Extended JSON obrigatório** (ObjectId/Date/Decimal128/Binary preservados).
- Editor de pipeline de aggregation (JSON). Export JSON/NDJSON.
- Builder visual de agregação e inferência de schema por amostra depois da v1 (ver "Depois da v1").
- Change streams depois da v1 (aba "Ao vivo", ver "Depois da v1").

## UI Redis

- DB 0–15 → chaves agrupadas por separador (padrão `:`, configurável).
- **Sempre `SCAN`, nunca `KEYS`.**
- Viewer/editor por tipo (string/hash/list/set/zset; stream somente leitura), TTL, renomear.
- Console de comandos (entra no histórico e nas abas). `INFO` formatado.
- Fora: pub/sub, monitor, módulos, export. Cluster e sentinel vieram depois (ver "Depois da v1").

## Segurança contra acidentes

1. Etiqueta de ambiente por conexão (`local/dev/staging/prod`) com cor; `prod` em vermelho na borda/abas/árvore.
2. Modo somente leitura no nível do banco: PG `default_transaction_read_only`, MySQL `SESSION TRANSACTION READ ONLY`, SQLite `mode=ro`, Mongo/Redis allowlist no Rust.
3. Confirmação de destrutivos (detectados com `sqlparser-rs`, não regex): DROP/TRUNCATE, UPDATE/DELETE sem WHERE, `deleteMany({})`, FLUSH*, etc. Em `prod`, **toda escrita** confirma, mostrando o comando gerado.

## Resultados grandes / queries lentas

- Editor: 1000 linhas iniciais, próximo lote via stream mantido aberto.
- Grade virtualizada; células grandes truncadas, completas em painel lateral.
- **Cancelamento real**: PG `pg_cancel_backend(pid)`, MySQL `KILL QUERY id`, Mongo `maxTimeMS` + `killOp`, SQLite/Redis só timeout.
- Timeout padrão 30 s por conexão (`0` desativa).

## Contrato de valores (Rust ↔ TS)

- `enum Cell` com tag `#[serde(tag = "t", content = "v")]`: Null, Bool, Int (string), Float, Decimal (string), Text, Bytes (preview), Date, Timestamp {value, tz}, Json, Array, ObjectId, Unknown.
- `Unknown` = exibido como texto, **não editável**.

## Arquitetura Rust

```
src-tauri/src/
  domain/      Cell, ConnectionConfig, Environment, AppError (thiserror)
  adapters/sql/{mod.rs (trait SqlAdapter), postgres.rs, mysql.rs, sqlite.rs}
  adapters/mongo.rs, adapters/redis.rs   (structs concretas, sem trait)
  use_cases/   regras: stage→SQL, somente leitura, destrutivos, paginação, export, histórico
  commands/    #[tauri::command] finos
  storage/     connections.json, keychain, history.sqlite
  registry.rs  RwLock<HashMap<ConnId, Live>>; enum Live { Sql(Box<dyn SqlAdapter>), Mongo, Redis }
```

- Fluxo: commands → use_cases → adapters. `AppError` serializado com tag (`NeedsConfirmation` abre o diálogo no front).
- Conexões abertas sob demanda, pool por conexão. Repo único (`src/` + `src-tauri/`).

## Testes

- Adapters: integração com `testcontainers` contra os 5 bancos reais (sem mock de driver).
- Use cases: `cargo test` com `FakeAdapter`.
- Parser de destrutivos: testes em tabela de casos.
- Front: Vitest + Testing Library com `invoke` mockado.
- Sem E2E na v1.
- Cobertura ≥ 70% (`cargo llvm-cov` + `vitest --coverage`), gate no CI (GitHub Actions, Linux).

## Distribuição

- Só Linux (AppImage + `.deb`), release via tag `v*` no GitHub Releases.
- Atualizações assinadas e auto-update (ver "Depois da v1"); sem builds de macOS/Windows.

## Notas de implementação

Decisões tomadas durante a implementação, que refinam ou adiam itens acima.

### M1

- **Protocolo texto no Postgres.** Toda query roda pelo simple query protocol (`sqlx::raw_sql`): o servidor renderiza cada valor em texto exato e o adapter só classifica pelo OID do tipo. Um único caminho de conversão para `Cell`, fidelidade total (numeric, int8, arrays).
- **Filtros da navegação** viram literais escapados com o algoritmo do `PQescapeLiteral` da libpq (aspas dobradas; com barra invertida, `E''`), porque o protocolo texto não aceita bind parameters. Identificadores sempre entre aspas. Testado contra injeção no teste de integração.
- **`Cell::Json` carrega o texto JSON**, não um valor parseado: números acima de 2^53 seriam arredondados pelo JavaScript. O front formata sem `JSON.parse`.
- **Sessão com `TimeZone=UTC`, `DateStyle=ISO`, `bytea_output=hex`** para que os textos sejam determinísticos. `timestamptz` aparece em UTC.
- **Somente leitura forçado em toda conexão no M1** (`FORCE_READ_ONLY` em `use_cases/sql.rs`). O M2 remove isso junto com a detecção de comandos destrutivos.
- **Sem trait `SqlAdapter` ainda**: `PostgresAdapter` é concreto. A trait é extraída no M3, quando MySQL e SQLite forem a 2ª e a 3ª implementação.
- **Script com vários comandos**: dividido por um lexer próprio (`split.rs`: strings, `E''`, `$tag$`, comentários aninhados); todos rodam na mesma sessão e o resultado mostrado é o do último.
- **Timeout** vale para o tempo até o primeiro lote de cada comando (e cancela no servidor). Lotes seguintes não contam, porque o usuário pode ficar lendo o resultado.
- **Cursor**: uma task tokio é dona da conexão e do stream do último comando. Fechar/abandonar o resultado cancela no servidor (`pg_cancel_backend`) e descarta a conexão em vez de drenar.
- **Tipos customizados** (enums, domínios, extensões) aparecem como `Unknown` (texto, não editável) no M1; resolver pelo catálogo entra no M2, quando edição importa.
- **TanStack Table adiado**: a grade só precisa de virtualização (TanStack Virtual). Entra quando houver redimensionar/fixar colunas.

### M2

- **Confirmação é uma resposta, não um erro**: `run_script`/`apply_changes` devolvem `NeedsConfirmation { reason, statements }` (em vez de `AppError::NeedsConfirmation`, como planejado). O front mostra o SQL exato e reenvia com `confirmed: true`.
- **O que pede confirmação** (`use_cases/guard.rs`, com `sqlparser`): DROP, TRUNCATE, UPDATE/DELETE sem WHERE, **ALTER TABLE … DROP COLUMN/CONSTRAINT** (adicionado), inclusive dentro de CTE e `EXPLAIN ANALYZE`. Em `prod`, toda escrita. Conexão somente leitura não confirma nada: o próprio banco recusa.
- **SQL que o parser não entende** cai na palavra-chave inicial: DROP/TRUNCATE são destrutivos; DELETE/UPDATE/ALTER pedem confirmação porque não dá para checar o WHERE.
- **Edição em stage**: linhas identificadas pela chave primária completa (validada no backend contra o catálogo); valores vão como literais texto que o Postgres converte para o tipo da coluna. Ordem: exclusões, alterações, inserções. Tudo numa transação e cada comando precisa afetar exatamente 1 linha, senão rollback com erro de conflito.
- **Editáveis**: tipos escalares modelados e enums. Arrays, bytea e tipos não modelados ficam somente leitura; tabela sem PK (ou com PK de tipo não editável) também. Paginação, ordenação e filtro travam enquanto houver alterações pendentes.
- **Tipos customizados**: enums e domínios resolvidos pelo `pg_type` (cache por conexão). Corrige um crash do M1: o sqlx entra em pânico ao chamar `kind()` num tipo não resolvido.
- **Abas** persistidas em `ui-state.json` (`tauri-plugin-store`, via `persist` do Zustand): tabelas, editores (com o SQL) e histórico. Resultados não persistem (o cursor morre com o app).
- **Histórico** em `history.sqlite` (sqlx sqlite): scripts executados (com erro, se houver) e edições salvas; o que ficou só na confirmação não entra. Sem limite de retenção por enquanto.
- **Salvar edições não tem timeout** (são poucas linhas por PK); o editor SQL continua com o timeout da conexão.

### M3

- **Enum em vez de `Box<dyn SqlAdapter>`**: `SqlConnection { Postgres, Mysql, Sqlite }` com despacho por `match` (macro `each!`). As engines são um conjunto fechado e métodos async atrás de `dyn` exigiriam futures boxeadas (`async_trait`). O contrato compartilhado é a trait `stream::Engine` (genérica, sem `dyn`): converter linhas, id de sessão, cancelar, descrever colunas.
- **Código compartilhado**: execução de script, cursor e streaming (`adapters/stream.rs`), transação das edições, montagem de SQL de navegação/edição (`sql_builder.rs`), dialetos (`dialect.rs`: aspas, literais, cast, parser) e um lexer configurável para dividir scripts (`split.rs`).
- **Custo por engine** (linhas não vazias): Postgres 389 + 261 de tipos; MySQL 376 + 83; SQLite 321. Acima dos ~300 combinados, mas ~200 de cada são consultas ao catálogo (information_schema, PRAGMAs), inerentes ao banco. Execução/navegação/edição/cancelamento custam ~60 linhas por engine.
- **MySQL**: protocolo texto (COM_QUERY), sessão em UTC, **sem tocar no `sql_mode`** (o sqlx adiciona PIPES_AS_CONCAT por padrão; desligado). Literais respeitam `NO_BACKSLASH_ESCAPES`, detectado na conexão. Cancelamento por `KILL QUERY`. Somente leitura via `SET SESSION TRANSACTION READ ONLY`. `DELIMITER` (convenção do cliente mysql) é aceito no editor para procedures. BOOLEAN é mostrado como número (é TINYINT(1)).
- **SQLite**: sem protocolo texto, cada valor é lido pela sua classe de armazenamento. Arquivo inexistente é erro (não cria banco vazio por engano de digitação). Somente leitura abre o arquivo em modo `ro`. Sem cancelamento (só timeout). Triggers com `BEGIN … END` são um comando só. Tabela sem PK declarada (só rowid) fica somente leitura.
- **Bug corrigido**: no MySQL, descartar o stream logo após o último resultado deixava a conexão "esperando" um pacote que nunca vem; o ping de devolução travava e o pool esgotava. Streams terminados agora são lidos até o fim antes de soltar (teste de regressão com 4× o tamanho do pool).

### M4

- **Formato dos documentos**: Extended JSON v2 relaxado, **exceto Int64, sempre `{"$numberLong": "…"}`**. O modo relaxado escreve Int64 como número simples: na volta, um Long pequeno viraria Int32 e um grande perderia precisão no JavaScript. Com a regra, número inteiro simples = Int32, número com ponto = Double, e o front pode usar `JSON.parse` com segurança. Ordem dos campos preservada (`serde_json` com `preserve_order`). Ida e volta testada contra o banco real, byte a byte.
- **Edição** substitui o documento inteiro por `_id` (`replaceOne`), um por vez, sem stage. Tem de casar exatamente 1 documento (senão conflito); o `_id` não pode mudar (nem de tipo). Note: o MongoDB compara números entre tipos, então `NumberLong(3)` encontra `_id: 3`.
- **Agregação** mostra até 1000 documentos (avisa quando há mais), sem cursor paginado. Cada execução leva o run id como `comment`; cancelar faz `currentOp` (`$ownOps`) + `killOp`. Timeout é `maxTimeMS` (no servidor). O mapeamento do erro 50 → timeout é testado em unidade: `maxTimeMS` não interrompe `sleep()` em JavaScript no servidor, então não dá para provocá-lo de forma determinística.
- **Regras de escrita**: somente leitura recusa insert/replace/delete e pipelines com `$out`/`$merge` (no app, já que o MongoDB não tem sessão read-only). `$out` substitui a coleção de destino: sempre pede confirmação. Em `prod`, toda escrita pede.
- **Connection string** (`mongodb+srv://…`): novo alvo `Target::Uri { database }`; a string inteira (com credenciais) vai para o keychain como segredo. No modo host/porta, autenticação contra `admin` e TLS conforme o modo (Mongo não tem TLS oportunista: "preferir" = sem TLS).
- **Registry**: `enum Live { Sql(SqlConnection), Mongo(MongoAdapter) }`. A árvore reaproveita `SchemaInfo` (databases = schemas, coleções = relações) e as abas de tabela abrem a tela de coleção quando a conexão é MongoDB.
- **Sem shell/console** do Mongo (fora do escopo): drop de coleção, `deleteMany` etc. não existem na UI, então não há outro caminho destrutivo além de `$out`.

### M5

- **Uma conexão multiplexada por database** (`SELECT` fixo na conexão), aberta no primeiro uso. Conexão quebrada (servidor reiniciou) é descartada e reaberta na próxima chamada. O timeout da conexão vira o `response_timeout` do driver: o comando é abandonado, mas **continua rodando no Redis** (não existe KILL para um comando em execução), e a mensagem diz isso.
- **Árvore**: a lateral lista os databases (`CONFIG GET databases`, 16 quando o CONFIG é bloqueado, comum em serviços gerenciados) com a contagem do `INFO keyspace`. Cada database abre uma aba com Chaves / Console / Servidor. As chaves vêm de `SCAN MATCH` em páginas (para em ~1000 chaves ou 10 chamadas, para um padrão raro não varrer o banco inteiro); "Carregar mais" continua do cursor. O agrupamento pelo separador é feito no front.
- **Valores**: até 1000 elementos por coleção e 1 MiB por string (avisa quando há mais; string truncada não é editável). Texto que não é UTF-8 aparece escapado como no redis-cli (`\xff`) e fica somente leitura. Nomes de chave não UTF-8 aparecem com perda e não abrem (raro; documentado no código).
- **Edição** imediata, sem stage (como no Mongo): `SET … KEEPTTL`, HSET/HDEL, LSET/RPUSH/LREM, SADD/SREM, ZADD/ZREM, EXPIRE/PERSIST, `RENAMENX` (não sobrescreve outra chave: conflito) e DEL. Renomear um campo/membro **adiciona o novo antes de remover o antigo**: o contrário esvaziaria a coleção e o Redis apaga chave vazia junto com o TTL (pego no teste). Vários comandos vão num MULTI/EXEC, mas o Redis **não tem rollback**: um comando que falha dentro do EXEC é reportado e os anteriores ficam aplicados. Sem checagem de concorrência: a última escrita vence. Criar chave recusa nome existente (EXISTS antes, com corrida aceita).
- **Console** (estilo redis-cli: aspas, `\xHH`, respostas numeradas) roda na conexão compartilhada do database, então recusa o que travaria ou mudaria o estado dela: SELECT, MULTI/EXEC/WATCH, pub/sub, MONITOR, AUTH/HELLO/QUIT/RESET e comandos bloqueantes (BLPOP…, XREAD BLOCK, WAIT). Conexão dedicada para o console fica para quando fizer falta.
- **Regras** (`use_cases/redis.rs`): somente leitura = allowlist de comandos de leitura (com subcomando, ex.: `CONFIG GET`); qualquer outro é escrita. Sempre pedem confirmação: FLUSHDB/FLUSHALL, SWAPDB, SHUTDOWN, DEBUG, `KEYS` (bloqueia o servidor; o app sempre usa SCAN), CONFIG SET/RESETSTAT/REWRITE, SCRIPT/FUNCTION FLUSH, REPLICAOF, CLIENT KILL. Em `prod`, toda escrita (console e edições), mostrando o comando gerado. Stream é somente leitura.
- **Histórico**: comandos do console e edições entram com `SELECT n` na frente. "Abrir no editor" só aparece para conexões SQL (corrige entradas do Mongo, que abriam o editor SQL).
- **Sem cancelamento** (como decidido): só timeout.

### M6

- **Export em streaming para arquivo**: o "Salvar como" vem do `tauri-plugin-dialog` (permissão só `dialog:allow-save`); o backend recebe o caminho e grava lote a lote, sem juntar o resultado em memória. Grava em `<arquivo>.part` e renomeia no fim: export que falha ou é cancelado não apaga um arquivo existente com o mesmo nome. Cancelável pelo mesmo `cancel_run` do editor (PG/MySQL no servidor, Mongo via `killOp`); sem timeout depois do primeiro lote. Cada export entra no histórico.
- **CSV (SQL)**, de dois lugares: a tabela (com o filtro e a ordenação da grade, todas as páginas) e o resultado do editor (reexecuta o script inteiro; só aceita leitura, checado com o `sqlparser`: escrita vai pelo editor e suas confirmações). Formato do `COPY … CSV` do Postgres: NULL é campo vazio e string vazia é `""`. Sem BOM (Excel pode errar acentos; LibreOffice pergunta a codificação).
- **Limites do CSV** (`ponytail` no código): a grade só carrega 32 bytes de cada binário, então blob maior sai como `<N bytes>`; arrays saem como `{a,b}` sem aspas nos elementos.
- **Mongo**: NDJSON ou array JSON, com filtro/ordenação/projeção aplicados, em Extended JSON (mesmo formato da tela: Int64 em `$numberLong`). Sem `maxTimeMS`: um export grande pode demorar.
- **Diagrama ER** (somente leitura, só SQL): botão no schema da árvore abre uma aba. Tabelas viram nós com colunas (PK/FK marcadas) e cada FK vira uma aresta tabela→tabela; FKs para outro schema aparecem listadas no nó em vez de desenhadas. Layout `layered` do elkjs, React Flow para pan/zoom/minimapa; duplo clique abre a tabela. As FKs passaram a vir estruturadas do catálogo (colunas, schema/tabela/colunas referenciadas) nos três engines.
- **Custo**: o diagrama consulta a estrutura de cada tabela (até 8 em paralelo). Uma consulta ao catálogo do schema inteiro por engine fica para quando schemas grandes ficarem lentos. React Flow + elk (~1,6 MB) carregam sob demanda, num chunk separado.

### Depois da v1

- **Queries favoritas**: uma coluna `starred` no próprio `history.sqlite`, não uma tabela ou tela de "snippets". A entrada favorita continua sendo uma execução do histórico (com conexão, duração e erro), e a busca no SQL já serve para achá-la; por isso não tem nome. Arquivos de antes da coluna recebem `ALTER TABLE … ADD COLUMN` ao abrir (checado pelo `pragma_table_info`, sem engolir erro), com teste contra um arquivo no formato antigo. Marcar um id inexistente é `NotFound`.
- **Ctrl+P = Ctrl+K**: os dois abrem a mesma paleta. Uma busca rápida própria do Ctrl+P chegou a existir e saiu ao juntar com a paleta, que já fazia o mesmo (só lista o que a lateral carregou, nunca conecta sozinha).
- **Timeout dos testes do front em 20 s** (`vite.config.ts`): é detector de travamento, não medida de desempenho. Com cobertura e arquivos em paralelo numa máquina ocupada, testes de UI levam de 1 a 6 s e o padrão de 5 s derrubava testes saudáveis ao acaso.
- **Copiar linhas como INSERT ou JSON**: a linha selecionada ou todas as carregadas, sempre o valor gravado (alterações pendentes não entram; linha adicionada e não salva não é copiável). O INSERT vem do backend (`copy_as_insert`) e não do front, porque os literais dependem do dialeto da conexão aberta (`E''` no Postgres, `NO_BACKSLASH_ESCAPES` detectado no MySQL): usa o mesmo `change_sql` das edições. No editor só há JSON, já que o resultado de uma query qualquer não tem tabela de destino. O JSON é montado como texto (Int64 e decimais exatos, colunas JSON como estão, `NaN`/`Infinity` como string). Binário que a grade só mostra em parte, array e tipo não modelado são recusados com o nome da coluna em vez de copiados com perda (no JSON, array e tipo não modelado saem, porque o texto já é exato). Área de transferência pelo `navigator.clipboard`, sem plugin; se o WebKitGTK recusar, o erro aparece ao lado do botão.
- **Fechar a janela deixa o Ordo na bandeja**: o X só esconde a janela (`CloseRequested` → `hide`), com conexões, abas e alterações pendentes intactas; "Abrir Ordo" na bandeja a traz de volta. Sair é pela bandeja ("Sair") ou por **Ctrl+Q**, que existe porque nem todo ambiente mostra a bandeja (GNOME sem a extensão de AppIndicator). Ctrl+Q com alterações pendentes pergunta antes, como o Ctrl+W, e não fecha abas: elas são persistidas e voltam na próxima abertura. "Sair" na bandeja encerra sem perguntar. Com o app escondido, abrir o Ordo de novo criaria um segundo processo: o `tauri-plugin-single-instance` faz a segunda abertura só mostrar a janela existente.
- **Túnel SSH pelo `ssh` do sistema**, não por uma crate SSH: assim valem o `~/.ssh/config` (aliases, `ProxyJump`), o agente e o `known_hosts` sem reimplementar nada. `ssh -N -L 127.0.0.1:<porta livre>:<host>:<porta>` com `BatchMode=yes` (não há terminal para perguntas: só chave ou agente; a senha SSH opcional veio depois, ver abaixo), `ExitOnForwardFailure=yes` e `StrictHostKeyChecking=accept-new` (confia no primeiro uso, recusa chave trocada). O `open` sobe o túnel e troca host/porta do alvo por `127.0.0.1:<porta>`; os adapters não sabem do túnel, exceto o Mongo, que liga `directConnection` para não descobrir membros do replica set por endereços inalcançáveis. Pronto = a porta local aceita conexão (o OpenSSH só abre o `-L` depois do login); se o `ssh` sai antes, o stderr dele vira o erro. O túnel vive na sessão aberta (`kill_on_drop`) e morre com o app mesmo em `exit` ou crash (`PR_SET_PDEATHSIG`). Só alvo host/porta: SQLite não tem rede e a URI do Mongo (`+srv`, vários hosts) não cabe num `-L`. TLS "verificar certificado" é recusado com túnel, porque o certificado não é de `127.0.0.1`.
- **Túnel SSH pelo `ssh` do sistema**, não por uma crate SSH: assim valem o `~/.ssh/config` (aliases, `ProxyJump`), o agente e o `known_hosts` sem reimplementar nada. `ssh -N -L 127.0.0.1:<porta livre>:<host>:<porta>` com `BatchMode=yes` (não há terminal para perguntas: só chave ou agente, sem senha SSH), `ExitOnForwardFailure=yes` e `StrictHostKeyChecking=accept-new` (confia no primeiro uso, recusa chave trocada). O `open` sobe o túnel e troca host/porta do alvo por `127.0.0.1:<porta>`; os adapters não sabem do túnel, exceto o Mongo, que liga `directConnection` para não descobrir membros do replica set por endereços inalcançáveis. Pronto = a porta local aceita conexão (o OpenSSH só abre o `-L` depois do login); se o `ssh` sai antes, o stderr dele vira o erro. O túnel vive na sessão aberta (`kill_on_drop`) e morre com o app mesmo em `exit` ou crash (`PR_SET_PDEATHSIG`). Só alvo host/porta: SQLite não tem rede e a URI do Mongo (`+srv`, vários hosts) não cabe num `-L`. TLS "verificar certificado" é recusado com túnel, porque o certificado não é de `127.0.0.1`.
- **Importar CSV numa tabela SQL** (Postgres, MySQL, SQLite), pelo botão "Importar CSV" da tabela (some em conexão somente leitura; o backend recusa de novo). O arquivo vem do "Abrir" do `tauri-plugin-dialog` (permissão `dialog:allow-open`) e é lido em streaming no backend, um registro por vez, por um leitor próprio em `adapters/csv.rs` em vez da crate `csv`: ela não diz se um campo vazio tinha aspas, e o formato é o mesmo do export (campo vazio sem aspas é NULL, `""` é texto vazio), então o que sai pelo export volta igual. Primeira linha é sempre o cabeçalho; o separador é adivinhado por ela (vírgula, ponto e vírgula, que é o que planilhas em pt-BR gravam, ou tab); BOM e CRLF aceitos; arquivo que não é UTF-8 é recusado com a linha. Linha em branco é pulada (`ponytail`: num arquivo de uma coluna, uma linha NULL ali se perde).
- **Fluxo**: prévia (cabeçalho e 10 linhas) → mapeamento coluna do arquivo → coluna da tabela (pelo nome, sem diferenciar maiúsculas; ajustável; as que ficam de fora recebem o padrão) → `import_csv` sem `confirmed`, que lê o arquivo inteiro (linha mal formada aparece antes de qualquer escrita) e devolve sempre um `NeedsConfirmation` com o total de linhas e o INSERT exato das 3 primeiras, **em todo ambiente**: é o comando antes do clique, e em prod o mesmo diálogo vem com a faixa de produção. Só a execução entra no histórico (`-- import CSV ← arquivo` e o começo do INSERT), não a revisão.
- **Uma transação, INSERT de várias linhas em lotes de 500**, com os literais de `quote_literal` (o mesmo caminho das edições, por dialeto). Cada lote roda sob um `SAVEPOINT`: se o banco recusa o lote, ele volta ao savepoint e repete o lote linha a linha só para achar a linha recusada; depois desfaz tudo. A coluna vem da posição do erro no Postgres (`invalid input syntax…` aponta o literal, e o app sabe onde cada literal está no INSERT); MySQL e SQLite já nomeiam a coluna na mensagem. O erro diz "linha N, coluna X: … Nada foi gravado". Sem timeout (como salvar edições). MySQL com MyISAM não tem transação: o que entrou fica.
- **Cancelar a importação**: `cancel_run` cancela o comando no servidor (PG/MySQL) e marca o run no registry; a importação olha a marca antes de cada lote, o que vale também para o SQLite, que não tem cancelamento no servidor. Cancelada, a transação é desfeita.
- **Atualizações assinadas pelo `tauri-plugin-updater`**, com o `latest.json` e os `.sig` publicados pelo `tauri-action` no próprio release (o endpoint é `releases/latest/download/latest.json`, sem servidor). O plugin atualiza o AppImage (troca o arquivo) e o `.deb` (`dpkg -i` via `pkexec`, que pede a senha de administrador); qualquer outra instalação (binário de `cargo build`, sem tipo de bundle) só fica sabendo da versão nova e vai para a página do release, em vez de fingir que atualizou. Sem `zip`: o AppImage vai sem compactar, como o Tauri 2 gera. A chave privada e a senha existem só nos secrets do GitHub (`TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`); a pública fica no `tauri.conf.json`. Os artefatos do updater só são gerados no workflow (`--config` com `createUpdaterArtifacts`), para que um `pnpm tauri build` local continue sem chave. Um `SHA256SUMS` dos pacotes vai junto, para quem baixa à mão. No app: uma verificação ao abrir, que não segura a inicialização e, se falhar (offline), só escreve no stderr; e "Procurar atualizações" na bandeja, que diz o resultado mesmo quando não há nada. Nada instala sem o "Instalar e reiniciar" de um diálogo com o número da versão, e alterações pendentes são perguntadas antes, como no Ctrl+Q. "Agora não" não lembra a escolha: a oferta volta na próxima abertura.
- **EXPLAIN visual** ("Explicar", Ctrl+Shift+E): a seleção ou a instrução sob o cursor, achada na árvore do lezer que o CodeMirror já mantém (a última instrução que começa antes do cursor; linha em branco depois de uma instrução ainda é ela). O backend confere que é uma instrução só (com o `split` do dialeto) e roda `EXPLAIN (FORMAT JSON)` no Postgres, `EXPLAIN FORMAT=JSON` no MySQL e `EXPLAIN QUERY PLAN` no SQLite pelo mesmo caminho do editor (timeout, cancelar, histórico), devolvendo uma árvore `PlanNode` com os rótulos do próprio banco ("Index Scan using users_pkey on users", "users (eq_ref)", "SCAN users"), custo, linhas estimadas e detalhes (Filter, Index Cond, key…). Custo é o do banco, que inclui os filhos; o **nó mais caro** é o de maior custo próprio (o do nó menos o dos filhos), marcado com a palavra "Mais caro" além do tom. O SQLite não estima custo nem linhas: a tela diz isso em vez de destacar um nó. No MySQL o JSON (formato 1) só tem custo por tabela e o total do bloco; os nós intermediários somam os filhos (`ponytail` no código). **ANALYZE só no Postgres**: o `EXPLAIN ANALYZE` do MySQL sai em texto (JSON só a partir do 8.3) e o SQLite não tem. ANALYZE executa a instrução, então passa pelo `guard.rs` como se ela fosse rodar (classificada pela instrução, porque o parser pode não conhecer as opções do EXPLAIN), e a confirmação mostra o EXPLAIN exato; sem atalho de propósito, só no menu do botão. Não é embrulhado em `BEGIN … ROLLBACK`: a confirmação diz o que vai rodar, e rodar outra coisa a desmentiria.
- **Formatar SQL** ("Formatar", Ctrl+Shift+F): a seleção ou o editor inteiro, numa transação só do CodeMirror (Ctrl+Z desfaz; a seleção formatada continua selecionada). **`sql-formatter` no front, não o `sqlparser` do Rust**: parse + `Display` (até o `{:#}`) descarta os comentários, reescreve o que o AST normaliza e recusa o que a gramática não conhece; o `sql-formatter` só mexe em espaços e quebras, conhece os três dialetos (`postgresql`, `mysql`, `sqlite`: `$$`, `E''`, crase, `#`, `[ident]`) e mantém a caixa das palavras-chave. Importado só com esses três dialetos: +86 kB minificado (+25 kB gzip) no chunk principal, sem carregar sob demanda porque o app lê do disco. Duas travas para não mudar a semântica: o texto formatado tem de ser igual ao original sem nenhum espaço em branco (senão nada muda e o motivo aparece ao lado do botão), e no MySQL um script com `DELIMITER` é recusado, porque o formatador junta essa linha (convenção do cliente mysql, não SQL) ao código vizinho. Erro de parse (SQL pela metade) aparece como "Não formatado: …" e some na próxima edição.
- **Pub/sub do Redis numa conexão própria por assinatura**: uma conexão em modo subscribe não roda mais nada, então cada assinatura (seção Pub/sub da aba do database) abre a sua, fora das conexões multiplexadas. As mensagens vão ao front por um `Channel` do Tauri, uma a uma; o front desenha em lotes de 200 ms e guarda só as últimas 1000 (pausar congela a tela e as novas esperam no buffer, com o mesmo limite). A assinatura termina ao parar, ao fechar a aba (trocar de seção não, para dar para mexer nas chaves e ver a notificação chegar) e ao fechar ou reabrir a conexão: o adapter guarda um `oneshot` por sessão e soltá-lo encerra a task, que avisa o painel. Canais e padrões são separados por espaço, então nome de canal com espaço não é assinável. Assinar só lê: vale em somente leitura e em `prod` sem confirmação. **PUBLISH** é escrita e passa pelas mesmas regras do console (recusado em somente leitura, confirmado em `prod` mostrando o comando, gravado no histórico); o console continua recusando SUBSCRIBE e afins, agora apontando para a seção.
- **Duplicar conexão** (menu da conexão na lateral): abre o formulário de conexão nova preenchido com a original, id novo e nome "<nome> (cópia)". O **ambiente volta vazio**: o regime de proteção é escolhido de novo, nunca herdado em silêncio (duplicar a prod para criar a staging não pode sair marcada como prod, nem o contrário). A senha ou URI salva não passa pelo front: com o campo vazio, o front manda `SecretChange::CopyFrom(<id da original>)` e o backend copia do keychain para o id novo ao salvar (ou só a lê, em Testar conexão). Digitar outra senha ou marcar "Não copiar a senha salva" vale como numa conexão nova.
- **Grupos de conexões**: um campo opcional `group` no próprio `ConnectionConfig` (`#[serde(default)]`, então o `connections.json` antigo carrega sem migração), não uma entidade "pasta" à parte: um grupo existe enquanto alguma conexão o usa, e renomear é editar as conexões. Sem aninhamento. No formulário, texto livre com as sugestões dos grupos em uso (`<datalist>` nativo). Na lateral, as conexões sem grupo ficam no topo e cada grupo vira uma pasta em ordem alfabética, um `treeitem` recolhível no mesmo teclado da árvore (as conexões dentro descem um `aria-level`). As pastas recolhidas ficam no `localStorage` e sobrevivem ao reinício, como a lateral recolhida; abrir uma conexão pela paleta abre a pasta dela.
- **Senha ou passphrase no túnel SSH**: um campo opcional, guardado no keychain sob `<id>:ssh` (separado da senha do banco, com o mesmo `SecretChange` Keep/Set/Clear/CopyFrom; desligar o túnel apaga a senha dele, e excluir a conexão apaga as duas). A mesma senha responde a qualquer pergunta do `ssh`: senha do usuário ou passphrase da chave. Ela chega ao `ssh` por **`SSH_ASKPASS` com `SSH_ASKPASS_REQUIRE=force`** (OpenSSH ≥ 8.4: usa o askpass sem terminal nem `$DISPLAY`), e o askpass é **o próprio binário do app**: o `main` vê a variável `ORDO_SSH_ASKPASS_SECRET`, imprime o valor e sai antes de abrir janela ou checar outra instância. A variável vai só no ambiente do processo `ssh` (e do que ele dispara, como o askpass e um `ProxyJump`, que recebe a mesma senha), nunca no do app. Alternativas descartadas: a linha de comando (`sshpass -p`, ou a senha num argumento do askpass) aparece no `ps` para qualquer usuário, enquanto o `/proc/<pid>/environ` só é legível pelo dono do processo; um script askpass num arquivo temporário teria que guardar a senha em disco ou ainda lê-la do ambiente, com um arquivo a mais para criar e apagar; uma crate SSH própria perderia o `~/.ssh/config`, o agente e o `known_hosts` (a razão de usar o `ssh` do sistema). Com `-N` não há canal de sessão, então a variável nunca chega ao servidor, nem com `SendEnv`. Com senha, o `BatchMode=yes` sai e entra `NumberOfPasswordPrompts=1`: senha errada falha na hora, em vez de três tentativas contra o servidor (fail2ban). Sem senha, o comando é o mesmo de antes. O teste ponta a ponta (sshd em container exigindo senha e, à parte, chave com passphrase) foi rodado à mão e não fica no repositório: o binário do `cargo test` é o do libtest, que não responde como askpass.
- **Importar JSON/NDJSON numa coleção Mongo**, pelo botão "Importar" da coleção (some em somente leitura; o backend recusa de novo). O arquivo é NDJSON (um documento por linha) ou um array JSON, detectado pelo primeiro caractere; um leitor em `ejson.rs` separa os documentos byte a byte (aspas e escapes contados), sem carregar o arquivo inteiro, e cada um passa pelo mesmo `parse_document` da edição: ObjectId, Date, `$numberLong`, Decimal128 e Binary mantêm o tipo, número inteiro simples é Int32 e com ponto é Double. O teste exporta, importa noutra coleção e exporta de novo: os arquivos saem idênticos byte a byte. Inteiro maior que Int64 sem `$numberLong` vira Double, como no `mongoimport`.
- **Revisão e execução** como no CSV: `import_documents` sem `confirmed` lê e valida o arquivo todo (documento quebrado aparece com a linha antes de qualquer escrita) e devolve o total e o primeiro documento **como será gravado** (`db.coll.insertMany([…, …])`, no formato da tela), em todo ambiente; em prod, com a faixa. Depois, `insertMany` ordenado em lotes de 1000, com o run id como `comment` (o `cancel_run` faz `killOp`) e a marca de cancelamento olhada antes de cada lote.
- **Sem transação no Mongo** (exigiria replica set): um documento recusado (ex.: `_id` duplicado) para a importação, e o erro diz a linha e quantos documentos já ficaram gravados ("linha 1201: E11000 … 1200 documentos já ficaram gravados"); cancelar diz o mesmo. O aviso também está no texto da confirmação.
- **Componente comum** (`features/import/ImportRun.tsx`): rodar sob um run id, "Cancelar importação", resultado e recarregar a tela, para o CSV e para os documentos.
- **Builder visual de agregação sobre o texto do pipeline**: os blocos são recortes do JSON do editor, achados por um varredor de profundidade/strings (`pipeline.ts`), e voltam ao editor juntados como texto. Nada passa por `JSON.parse` + `stringify`, que trocaria `1.0` (Double) por `1` (Int32) e arredondaria inteiros acima de 2^53; o `JSON.parse` só valida. O JSON continua sendo o que roda: editar o texto refaz os blocos, editar um bloco reescreve o texto (com a formatação do builder). Estágio desligado não existe em JSON, então fica só no builder e **fora do texto e da execução**, guardando o lugar entre os ligados quando o texto muda. Bloco com JSON inválido não mexe no pipeline (que mantém a última versão válida) e bloqueia Executar e a prévia. Reordenar é por botões (o foco segue o estágio movido), não por arrastar. A prévia roda os estágios ligados até o escolhido mais `{ "$limit": 20 }`, dito na tela, pelo mesmo `run_aggregation` (com cancelamento, timeout e histórico); se algum deles for `$out`/`$merge`, a prévia é recusada no front, porque uma prévia não escreve e nada pode vir depois desses estágios. Executar segue as regras de escrita e confirmação de sempre. Prévia automática a cada edição ficou de fora: em produção, cada tecla viraria uma agregação.
- **Schema da coleção por amostra** (aba Schema): `aggregate([{ "$sample": { "size": N } }])`, com N de 1 a 10 000 (padrão 100, ajustável), e o comando aparece na tela antes de rodar. O Rust percorre os documentos (`adapters/mongo/schema.rs`) e devolve cada caminho (`a.b` dentro de objetos, `a[]` para elementos de array, `a[].b`…) com os tipos BSON pelo nome do `$type`, quantos documentos da amostra têm o caminho e o primeiro exemplo escalar em Extended JSON (mesmo formato da tela, Int64 em `$numberLong`), cortado em 200 caracteres com aviso. Tipos contam ocorrências (os elementos de um array contam um a um); presença conta documentos. A tela diz que é uma amostra aleatória e não o schema: o MongoDB não impõe um e campos raros podem não aparecer. É leitura (vale em conexão somente leitura), não entra no histórico (como a navegação), usa `maxTimeMS` do timeout da conexão e o run id como `comment`, então Cancelar faz `killOp` como na agregação. Roda só ao clicar em Amostrar, nunca ao abrir a aba. O limite de 10 000 existe porque `$sample` acima de ~5% da coleção ordena os documentos em memória no servidor, e a amostra inteira fica em memória no Rust até ser resumida (só o resumo vai para a tela).
- **Índices do Mongo: criar e remover.** A aba Índices da coleção cria um índice por vez (chaves em ordem, cada uma com direção `1`/`-1` ou tipo `text`/`hashed`/`2dsphere`/`2d`; `unique`, `sparse`, TTL `expireAfterSeconds`, `partialFilterExpression` em Extended JSON e nome opcional, gerado das chaves como os drivers fazem: `email_1`). O backend monta o comando `createIndexes` e roda exatamente esse documento com `runCommand`; o formulário mostra o comando enquanto é preenchido, pedido ao próprio backend (`index_statement`, sem conexão), para o texto exibido não ser uma cópia do front que possa divergir. Fora de prod, criar roda sem segunda confirmação (o comando já estava na tela); em `prod`, confirma. Remover (`dropIndexes` por nome) é destrutivo e sempre confirma; `_id_` é recusado (o servidor também recusa, mas a mensagem é nossa) e `*` também, porque o `dropIndexes` lê `*` como "todos os índices". Somente leitura recusa os dois antes de chegar ao servidor. Combinações inválidas (`sparse` com `partialFilterExpression`, TTL em índice composto) ficam com a validação do servidor, cuja mensagem aparece no formulário. A lista passou a mostrar `SPARSE`, `expireAfterSeconds` e `partialFilterExpression` além de `UNIQUE`. Sem `maxTimeMS`: criar índice numa coleção grande pode demorar. Criar e remover entram no histórico.
- **Change streams no Mongo: aba "Ao vivo" da coleção.** "Iniciar" abre um `watch` na coleção com um pipeline opcional em Extended JSON (`$match`, `$project`…) e cada evento chega por um `tauri::ipc::Channel` (o app não tinha padrão de eventos do backend além do `close-requested`; o canal é por chamada, ordenado e morre com ela). O evento mostra operação, `documentKey._id`, `fullDocument` (insert/replace) ou `updateDescription` (update, o diff; sem `updateLookup`, que buscaria o documento inteiro a cada update), e o horário (`wallTime`, ou `clusterTime` em servidores antes do 6.0), tudo em Extended JSON como no resto da tela. O backend lê o evento como documento cru, porque um pipeline pode remodelar o evento além da forma tipada do driver. Abrir o stream é esperado no comando: um servidor standalone falha ali (erro 40573) e a mensagem diz que change streams exigem replica set ou cluster fragmentado, com o texto do servidor. Depois, uma task lê o stream; erro no meio vira uma mensagem final no canal. **Fechamento**: a task fica no registry; `stop_watch`, desconectar (inclusive prod ao esconder a janela) ou o canal morto a abortam, e soltar o stream fecha o cursor no servidor. O painel não fica montado fora da sua aba: sair da seção, fechar a aba ou "Parar" encerram o stream (o front espera a abertura terminar antes de mandar o `stop_watch`, para o stop não chegar antes). **Memória**: até 500 eventos, os mais antigos saem. "Pausar" só congela a lista na tela; os eventos continuam chegando (até o mesmo limite) e o contador mostra quantos estão fora da tela. É leitura: vale em conexão somente leitura e em prod sem confirmação. Teste de integração com um replica set de um nó (`Mongo::repl_set()` com `directConnection`, porque o membro se anuncia pelo nome do container); o `dev/demo` é standalone e mostra a mensagem de erro.
- **Redis Cluster** como um `Target` próprio (`redisCluster`: nós semente e usuário), não um campo a mais no `network`: o cluster não tem host/porta únicos nem database (só o 0), e o `match` sobre o alvo já separa o que vale para cada um. Feature `cluster-async` da crate `redis`; um `ClusterConnection` roteia cada comando pela chave, segue MOVED/ASK e se reconecta sozinho. Comandos sem chave seguem a política da crate: `DBSIZE` soma os primários (contagem da árvore), `KEYS`/`FLUSHDB` vão a todos, `INFO` no console responde por nó. O painel de INFO mostra o primeiro primário e diz qual. O `SCAN` percorre **cada primário** (endereços do `CLUSTER SLOTS`, ordenados), um depois do outro, com o cursor `"<primário>:<cursor>"`; o `TYPE` de cada chave vai em comandos concorrentes roteados pela chave, já que um pipeline com chaves de slots diferentes é recusado. Comando multi-chave fora do mesmo slot volta com o `CROSSSLOT` do servidor e uma explicação (hash tag). MGET/DEL/EXISTS com várias chaves funcionam: a crate divide por slot. Túnel SSH é recusado (Rust e formulário): os nós anunciam os próprios endereços, que um `-L` não alcança. Testes: três primários num contêiner, cada um na mesma porta dentro e fora e anunciando `127.0.0.1`.
- **Redis com Sentinel** também é um `Target` próprio (`redisSentinel`: sentinels, nome do master, database e usuário). Feature `sentinel` da crate `redis`: o `SentinelClient` pergunta o master aos sentinels e confere o `ROLE` dele. A resposta vira um servidor standalone comum (uma conexão por database), mas o master é **perguntado de novo a cada conexão aberta**, então a reconexão depois de um failover chega ao master novo; o cabeçalho da aba mostra o master resolvido (`redis_master`), porque é para ele que vão as escritas. Senha do sentinel é separada da do Redis: entrada própria no keychain (`<id>:sentinel`, ao lado da `<id>:ssh` do túnel), com o mesmo `SecretChange`: duplicar a conexão a copia, sair do modo sentinel a apaga, excluir a conexão apaga todas. Com três segredos, `open`/`test_connection` recebem um `Secrets` (senha, SSH, sentinel) em vez de `Option<String>` posicionais, que o compilador deixaria trocar. TLS vale para sentinels e master. Túnel SSH é recusado, pelo mesmo motivo do cluster. Fica de fora: conexões já abertas em outros databases não migram sozinhas se o master antigo continuar de pé como réplica (escrita volta `READONLY`; reconectar resolve). Teste: master e um sentinel num contêiner, cada um com senha própria.
- **DDL na aba Estrutura**, com botão de copiar: o texto que o próprio banco guarda quando existe. MySQL: `SHOW CREATE TABLE` (que também responde por views). SQLite: o `sql` do `sqlite_master` como foi digitado, a tabela primeiro e depois seus índices e triggers (índices automáticos de PK/UNIQUE não têm texto). Postgres não guarda o `CREATE TABLE` (só o `pg_dump` escreve um), então ele é **reconstruído a partir do catálogo** com os deparsers do próprio servidor (`format_type`, `pg_get_expr`, `pg_get_constraintdef`, `pg_get_indexdef`): colunas com tipo, default, identity, coluna gerada e NOT NULL; PK, UNIQUE, CHECK, FK e EXCLUDE como `CONSTRAINT`; `PARTITION BY`; índices que não sustentam constraint. Views vêm do `pg_get_viewdef`. A UI diz que é reconstruído e o que fica de fora (permissões, dono, herança, opções de armazenamento, `OPTIONS` de tabela estrangeira). O teste de integração apaga a tabela, roda o DDL reconstruído e compara a estrutura com a original; roda num Postgres 16, porque o 11 padrão do testcontainers não tem colunas geradas (`attgenerated` é lido por `to_jsonb` para o 11 continuar respondendo).
- **Contagem de linhas na navegação**: ao abrir, a estimativa barata que o banco já guarda, marcada com "≈" (lida como "cerca de"): `reltuples` no Postgres (nenhuma para views, tabela particionada ou tabela nunca analisada; servidores antes do 14 dizem 0 em vez de -1) e `TABLE_ROWS` no MySQL (amostrada pelo InnoDB e guardada em cache por até `information_schema_stats_expiry`, um dia por padrão). O SQLite não tem estimativa. A estimativa é da tabela inteira, então some quando há filtro. O `COUNT(*)` exato só roda quando pedido ("Contar"), com o filtro ativo, pelo mesmo caminho do editor: cancelável por `cancel_run` (o botão vira "Cancelar") e sujeito ao timeout da conexão, porque pode varrer a tabela toda. O número viaja como texto (o specta não aceita u64) e é formatado com `BigInt`. A contagem recomeça quando o filtro muda ou edições são salvas; trocar de página não a apaga.
- **Edição de schema pela UI** (aba Estrutura e "Nova tabela…" no menu do schema): criar tabela, adicionar, renomear e remover coluna, mudar tipo, default e NULL, criar e remover índice. Cada alteração é um `SchemaChange` que o backend transforma em **um** comando DDL (`sql_builder::schema_sql`, nomes entre aspas do dialeto; tipo, default, `USING` e definição entram como SQL digitado, porque é isso que o usuário quer escrever). Um `;` que gere um segundo comando é recusado. `alter_schema` sem `confirmed` **sempre** devolve a confirmação com o comando exato, mesmo em `local`: o motivo vem do `guard.rs` quando há (DROP COLUMN e DROP INDEX são destrutivos; em `prod`, toda alteração), senão "confira o comando". Conexão somente leitura é recusada antes de gerar o DDL (o banco também recusaria: o `READ ONLY` do MySQL barra DDL, testado). Roda pelo caminho do editor (timeout da conexão) e entra no histórico. Cancelar a confirmação volta ao formulário preenchido. Com alterações pendentes na grade da mesma tabela, a estrutura fica travada até salvar ou descartar.
- **Limites por engine, ditos na UI**: o Postgres altera tipo (com `USING` opcional), default e NULL um de cada vez. O MySQL não tem `ALTER COLUMN … SET NOT NULL`: tipo e NULL mudam com `MODIFY COLUMN`, que reescreve a coluna inteira, então o formulário começa da definição atual tirada do `SHOW CREATE TABLE` (default, comentário e AUTO_INCREMENT incluídos) e o usuário edita o texto todo, em vez de o app remontar a definição e perder o que não conhece; default usa `ALTER COLUMN … SET/DROP DEFAULT`. O SQLite só renomeia e remove coluna (além de criar e remover índice): tipo, default e NULL exigem recriar a tabela, e a tela diz isso em vez de oferecer a opção. Índices automáticos do SQLite (`sqlite_autoindex_*`) não têm "Remover". Renomear e remover tabela, renomear índice e constraints vieram em seguida (abaixo); recriar tabela no SQLite continua pelo editor SQL.
- **Tabela, nome de índice e constraints na aba Estrutura**: renomear e remover a tabela (a aba segue o novo nome ou fecha junto), renomear índice e adicionar ou remover chave estrangeira, CHECK e UNIQUE, pelo mesmo `alter_schema`. `DROP TABLE` e `ALTER TABLE … DROP CONSTRAINT` são destrutivos pelo `guard.rs`; renomear não é. O `RENAME INDEX` do MySQL o `sqlparser` não entende, então cai no fallback seguro e pede confirmação como destrutivo ("não foi possível analisar"), com teste dizendo isso. No MySQL o renome da tabela leva o database junto (`RENAME TO \`db\`.\`novo\``), senão um nome sem database iria para o database padrão da sessão. A chave estrangeira do formulário liga **uma** coluna a uma coluna de outra tabela do mesmo schema, com `ON DELETE`de uma lista fechada (padrão, RESTRICT, CASCADE, SET NULL), não SQL digitado; chave composta ou para outro schema vai pelo editor (o backend já aceita listas).`TableStructure`ganhou`constraints`: UNIQUE e CHECK no Postgres; só CHECK no MySQL, onde UNIQUE já aparece como índice (servidores antes do 8.0.16 não têm `CHECK_CONSTRAINTS`: o erro 42S02 vira lista vazia, só esse); nenhuma no SQLite. Remover constraint no MySQL usa a forma genérica `DROP CONSTRAINT` (8.0.19+). O SQLite não renomeia índice nem adiciona ou remove constraint sem recriar a tabela: a tela diz isso, e lembra que um índice UNIQUE faz o papel do UNIQUE.
- **MONITOR numa seção própria**, na mesma estrutura de sessão ao vivo do pub/sub (conexão dedicada, `Channel`, mesma `stop_redis_session`, últimas 1000 linhas na tela). Como pesa no servidor a cada comando executado, o aviso fica sempre visível e o backend o encerra sozinho após **60 s ou 10 000 linhas**, o que vier primeiro; a seção não fica montada, então sair dela (ou fechar a aba) também para. Não altera dados: vale em somente leitura; em `prod` pede confirmação antes de começar, mostrando `MONITOR`. Não entra no histórico, que é de comandos que mexem no banco ou o consultam. As linhas vão como o servidor as escreve, sem parse. Em cluster é recusado: MONITOR só vê o nó em que roda, então mostraria uma parte do tráfego como se fosse tudo; atrás do Sentinel vai para o master atual.
- **Export de chaves do Redis em NDJSON**, pelo mesmo caminho dos outros exports ("Salvar como", `.part` + rename, `cancel_run`, histórico). Percorre o database com `SCAN MATCH` (o padrão da busca, todas as páginas, não só as carregadas; nunca `KEYS`; em cluster, um primário depois do outro, com o mesmo cursor `<nó>:<cursor>` da árvore) e escreve uma linha por chave: `{"key", "type", "pttl", "value"}`. `pttl` em milissegundos (`null` = sem expiração). O valor vem inteiro, sem o limite de 1000 elementos da tela: string como texto; hash e zset como pares `[campo, valor]` / `[membro, score]` (pares, e não objeto, porque nome de campo pode ser binário; score como o Redis escreve, `"inf"` inclusive, sem passar por float); list e set como arrays; stream como `[{"id", "fields"}]`. **Todo texto que não é UTF-8** (nome da chave, valor, campo, membro) vira `{"$base64": "…"}`; texto UTF-8 é sempre string JSON, então não há ambiguidade. Tipos de módulo saem com o `DUMP` em `dump` no lugar de `value` (restaurável com `RESTORE`, sem modelar o tipo). Cancelar não interrompe um comando no servidor: o loop confere entre uma chave e outra (`cancel_run` no Redis só encerra o run). Só lê: vale em somente leitura e em `prod` sem confirmação. Limites (`ponytail` no código): o valor de uma chave fica inteiro em memória enquanto sua linha é escrita, e o `SCAN` pode devolver uma chave duas vezes durante um rehash, que então aparece duplicada no arquivo.
- **Módulos do Redis**: a seção Servidor lista o `MODULE LIST` (nome e versão como o módulo informa, ex.: RedisJSON 2.6.9 = `20609`); serviço que recusa `MODULE` mostra o erro ali sem derrubar o INFO. Chave de tipo de módulo que o app não modela (Bloom, TimeSeries…) aparece na árvore com o nome do tipo (`MBbloom--`) e abre só com esse nome e o TTL; TTL, renomear e excluir continuam valendo, porque não dependem do tipo. **RedisJSON** (`ReJSON-RL`) abre no editor JSON do Mongo (CodeMirror): o texto do `JSON.GET` vai como string, **nunca parseado**, e o front só o reindenta com um percorredor de caracteres (sem `JSON.parse`, que arredondaria inteiros de 64 bits); acima de 1 MiB aparece cortado e somente leitura, como string. Salvar faz `JSON.SET chave $ <texto>` (substitui o documento e mantém o TTL), com as regras de toda edição: recusado em somente leitura, confirmado em `prod` mostrando o comando. O backend valida a sintaxe e **recusa inteiro que não cabe em 64 bits**: o RedisJSON o gravaria como double arredondado (pego no teste), então a mensagem sugere gravar como string. Comandos de leitura do RedisJSON (`JSON.GET`, `JSON.TYPE`…) e `MODULE LIST` entram na allowlist de somente leitura. Testado contra `redis/redis-stack-server`.
- **Seguir chave estrangeira na grade** (SQL): célula de coluna que faz parte de uma FK ganha um ícone (o "↗" no canto) e **Alt+Enter**, que abrem a tabela referenciada **já filtrada** pela linha apontada, com o filtro comum da navegação (`=` em cada coluna da chave: FK composta filtra por todas). O inverso é o menu **Referências** da barra de status (ou **Alt+Shift+Enter** na grade): lista as FKs que apontam para a tabela (`pedidos (cliente_id)`) e abre a escolhida filtrada pela linha selecionada. Tudo no front, sem comando novo: as FKs de saída vêm da estrutura que a aba já carrega, e as de entrada da mesma leitura do diagrama ER (`schema_diagram`), pedida só quando o menu abre. Limites (`ponytail` no código): o inverso só enxerga o **schema da tabela** (como o diagrama), e o menu diz isso; coluna que está em duas FKs segue a primeira. Vale o valor **gravado**, não o editado e não salvo; linha adicionada e não salva não navega. NULL não navega (numa FK composta basta um NULL: pelo `MATCH SIMPLE` ela não aponta para nada), nem binário que a grade só mostra em parte ou array; o Alt+Enter diz o motivo. No SQLite a FK pode não nomear as colunas referenciadas (aponta para a PK implícita): a PK vem da estrutura da outra tabela. O destino é a aba da tabela (aberta ou não), que recomeça com o filtro; se ela tem **alterações pendentes**, nada muda e o motivo aparece na origem, porque as edições em stage são presas à posição das linhas. O filtro aplicado assim não é persistido com as abas, como os filtros digitados.
- **Sessões ativas** ("Sessões ativas" no menu da conexão; não existe para SQLite, que não tem servidor): uma aba por conexão com id, usuário, banco, estado, tempo no estado, cliente e query, lidos pelo próprio servidor. Postgres: `pg_stat_activity` (só `client backend`). MySQL: `information_schema.PROCESSLIST` (sem o privilégio `PROCESS`, o servidor mostra só as threads do próprio usuário). Mongo: `$currentOp` com `allUsers` (operações em andamento, não conexões ociosas; exige o privilégio `inprog`, senão o erro do servidor aparece na tela). Redis: `CLIENT LIST` e `SLOWLOG GET 128` num pipeline só, numa seção "Comandos lentos". A tela mostra o comando que leu a lista. **A sessão do app** é a que rodou a listagem (`pid = pg_backend_pid()`, `ID = CONNECTION_ID()`, o `CLIENT ID` no mesmo pipeline, a operação marcada com o `comment` `ordo-sessoes`), marcada "Este app" e sem botão de encerrar; as outras conexões do pool do app aparecem com o `application_name`/`appName` `ordo` no cliente. Atualizar é manual; a atualização automática (5, 15 ou 60 s) só liga quando o usuário escolhe, e some com a aba. Tempo é o do estado atual (PG `state_change`, MySQL `TIME`), o de execução no Mongo (`secs_running`) e o ocioso no Redis (`idle`).
- **Encerrar** é escrita: o botão some em conexão somente leitura e o backend recusa de novo. Cada engine oferece o que faz: Postgres `pg_cancel_backend`/`pg_terminate_backend`, MySQL `KILL QUERY`/`KILL`, Mongo `killOp` (encerra a operação; a conexão do cliente fica), Redis `CLIENT KILL ID` (não há como parar um comando em execução, só fechar o cliente). O id vem da lista, mas o backend o valida (número; no Mongo também `shard:número`) antes de montar o comando, nunca o cola como veio. Em `prod`, a confirmação mostra o comando exato; no Redis `CLIENT KILL` já era destrutivo no console, então confirma em todo ambiente, como lá. `pg_cancel_backend` que responde `false` (pid que já terminou) e `CLIENT KILL` que fecha 0 clientes viram "não encontrado". Cada encerramento entra no histórico. Em Redis Cluster a lista é recusada (`ponytail`): cada nó tem os seus clientes e o seu slowlog.
- **Comparar schema entre duas conexões SQL** ("Comparar com outro schema…" no menu do schema): aba com origem (de onde foi aberta) e destino escolhidos por conexão e schema, só entre conexões da **mesma engine** (o backend recusa duas engines: tipos e DDL de uma não valem na outra). Só lê: a mesma leitura do catálogo da aba Estrutura e do diagrama (`table_structure` de cada tabela, até 8 em paralelo), sem comando novo nos adapters. Lista as tabelas só de um lado e, nas tabelas em comum, as diferenças de coluna (tipo, NULL e default, comparados como o catálogo os escreve), chave primária, índices, constraints (UNIQUE/CHECK) e chaves estrangeiras, casados **pelo nome** e comparados pela definição. Schemas de nomes diferentes (dev, prod) não fazem toda definição diferir: o qualificador do próprio schema (`ON public.users`, `REFERENCES dev.teams`, `nextval('dev.s')`) sai antes de comparar (`ponytail`: troca de texto, então um literal com `<schema>.` também muda). Views, sequências, tipos, funções, triggers e permissões não entram, e a tela diz isso.
- **DDL sugerido só no Postgres** (`ponytail` no código; MySQL e SQLite listam as diferenças e a tela diz que o DDL não é gerado neles, em vez de esconder): leva o destino ao estado da origem, **mostrado com botão de copiar e nunca executado por esta tela** (dito na tela), para rodar pelo editor SQL com as confirmações de sempre. Tabela nova vem inteira do `CREATE TABLE` reconstruído da aba Estrutura, com o schema trocado pelo do destino; o resto sai dos geradores da edição de schema (`sql_builder::schema_sql`: ADD/DROP COLUMN, `TYPE` sem `USING`, `SET/DROP DEFAULT`, `SET/DROP NOT NULL`, DROP INDEX/CONSTRAINT/TABLE), e índices e constraints novos vêm da definição do catálogo da origem (`pg_get_indexdef`, `pg_get_constraintdef`) apontada para o destino. Ordem: tabelas novas; por tabela, o que sai ou muda primeiro, depois colunas, constraints e índices; chaves estrangeiras por último (podem apontar para tabelas novas); por fim `DROP TABLE` das tabelas que só o destino tem, marcadas com um comentário "destrutivo". Índice que sustenta constraint vai e volta com ela (o da PK é reconhecido pelo nome padrão `<tabela>_pkey`). Chave primária diferente vira um comentário para ajustar à mão. Limites: tabelas novas que se referenciam podem precisar de outra ordem; default com `nextval` de sequência que o destino não tem falha ao rodar (colunas identity vêm completas no `CREATE TABLE`). O teste de integração cria dois schemas, roda o DDL sugerido no destino e compara de novo: nenhuma diferença.
